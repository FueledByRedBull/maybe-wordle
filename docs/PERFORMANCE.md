# Predictive performance profile

This document records suggestion-kernel performance separately from solve-quality evidence. It does not evaluate the sealed test and does not support a mean-guesses claim.

The canonical machine-readable artifact is [`benchmarks/predictive/release-performance-v1.json`](../benchmarks/predictive/release-performance-v1.json). It was generated by a dedicated release benchmark executable whose global allocator delegates to `System` while counting allocation calls and requested bytes.

## Recorded workloads

The 2026-07-26 Windows x86-64 run used an AMD Family 25 Model 97 processor.

| Workload | Survivors | Regime | Cold wall | Warm wall | Process CPU/call | Cycles/call | Allocations/call | Allocated/call | Peak working set |
| --- | ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `proxy-root` | 2,358 | proxy | 39.298 ms | 36.724 ms | 467.448 ms | 2.077B | 18,377 | 7.16 MiB | 73.7 MiB |
| `bounded-lookahead-15` | 15 | lookahead | 96.534 ms | 94.153 ms | 108.073 ms | 466.5M | 22,959 | 27.42 MiB | 81.5 MiB |
| `pooled-exact-15` | 15 | exact | 184.997 ms | 189.173 ms | 270.833 ms | 863.8M | 23,346 | 38.15 MiB | 83.0 MiB |

Process CPU can exceed wall time because proxy scoring uses Rayon worker threads. Peak working set is a process-lifetime high-water mark, so later workloads inherit earlier setup memory.

Cold-to-warm wall ratios were `1.070`, `1.025`, and `0.978`. Warm page faults per call were approximately `1,641`, `3,712`, and `4,659`; these reflect allocation and virtual-memory activity, not hardware cache misses. The pooled-exact cold/warm inversion is small enough to treat as measurement noise.

## Interpretation

- The normal large-state proxy root is within the current interactive latency envelope on this machine.
- Bounded lookahead on the replayable tractable posterior remains under 100 ms warm on this machine, but its continuation work now costs more wall time than the highly parallel full-posterior proxy root.
- Pooled exact search is the most expensive measured regime, but remains below 200 ms on the replayable 15-answer state.
- Allocation volume grows from about 7.2 MiB at the proxy root to 38.2 MiB in pooled exact. Reusing scratch vectors and candidate buffers is the clearest low-level opportunity, but solve-quality studies take priority because the current working-set envelope is modest and premature rewrites would add risk.

## Reproduction

From the repository root in PowerShell:

```powershell
$env:MAYBE_WORDLE_PROFILE_OUTPUT = 'benchmarks/predictive/release-performance-v1.json'
cargo bench --bench performance_profile
Remove-Item Env:MAYBE_WORDLE_PROFILE_OUTPUT
```

The artifact records the exact benchmark executable fingerprint, input/config fingerprints, git revision/dirty state, platform, CPU identifier, observations, and detected search regime.

`cargo test --all-targets` invokes benchmark binaries in a debug profile, so this benchmark exits early in that context unless `MAYBE_WORDLE_PROFILE_OUTPUT` is explicitly set. This prevents unoptimized test timings from overwriting the release artifact.

## Limitations

- Relaxed atomic allocation counters add overhead; allocation results are best treated as comparative workload evidence.
- Process CPU and cycles include Rayon worker threads.
- The installed Windows tools included WPR but not an automated WPA exporter or equivalent hardware-counter analyzer. Therefore no L1/L2/LLC miss rate is claimed. Cold/warm ratios and page faults are the available cache-behavior proxies.
- Peak working set cannot be reset between workloads inside one process.
