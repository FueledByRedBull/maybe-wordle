# Predictive performance profile

This document records suggestion-kernel performance separately from solve-quality evidence. It does not evaluate the sealed test and does not support a mean-guesses claim.

The historical July machine-readable artifact is [`benchmarks/predictive/release-performance-v1.json`](../benchmarks/predictive/release-performance-v1.json). It was generated by a dedicated release benchmark executable whose global allocator delegates to `System` while counting allocation calls and requested bytes. Those measurements do not validate the September finite-horizon implementation.

## September finite-policy diagnostic

The raw benchmark diagnostics below are local-only; their paths are shown as inline code and are not part of a public clean checkout.
The first eight-state release profile is retained in
`../benchmarks/predictive/release-gameplay-latency-v1.json`.
It uses synthetic reachable observations at puzzle date August 1, not held-out
outcomes, with three samples per state and budget. The reported sample p95 is
therefore the maximum of three observations, not a gameplay population estimate.
The measurement includes request preparation and response construction; its search
budgets are 30 ms preview, 250 ms Fast and 2,000 ms Strong.

OLATE/10001 medians were 34.64, 256.01 and 2,006.16 ms respectively. However, all
three budgets returned only an unevaluated heuristic for this state. Root and
fallback-tail states also failed to complete a rollout even at Strong. This is a
negative integration result, not evidence that rollout quality is ready for release.
Millions of exact-endgame memo hits motivated direct one/two-answer terminal rules.
Memory in this initial artifact remains a shared-process diagnostic; later isolated
phase measurements are recorded below.

The matched terminal-rule rerun is
`../benchmarks/predictive/release-gameplay-latency-terminal-v1.json`.
The three-answer exact-band Fast median fell from 76.02 to 27.22 ms; Strong fell
from 78.15 to 29.83 ms. The 13-answer band completed at Fast, and hard-mode Fast
returned a completed upper-bound policy rather than an unevaluated action. Root,
OLATE and fallback-tail still returned only heuristics. These are development
diagnostics from distinct executable hashes, not promotion evidence or isolated
memory comparisons.

The next diagnostic,
`../benchmarks/predictive/release-gameplay-latency-shared-proxy-v1.json`,
combined shared proposal scoring with exact bound-attainment stopping. It reduced
the 13-answer Fast median to 85.23 ms but still completed no broad-state rollout.
The subsequent
`../benchmarks/predictive/release-gameplay-latency-incumbent-v1.json`
evaluates the cheap baseline policy before exact refinement. Root, OLATE/10001 and
fallback-tail returned completed upper-bound policies in every Fast and Strong
sample (three each), rather than unevaluated heuristics. They still exhausted their
search budgets; only one root candidate completed, so improvement over the baseline
and broader alternative coverage remain unproved. These runs do not establish solve
quality, and the combined changes are not isolated single-factor speed claims.

`../benchmarks/predictive/release-gameplay-latency-shortlist-v1.json`
then moves cheap rollout comparison across the shortlist ahead of exact refinement.
Every Strong sample completed 17 root candidates on root, OLATE and fallback-tail;
Fast completed 3, 9 and 9 respectively, versus one in the preceding run. The values
remain feasible-policy upper bounds. More compared candidates at the same budget
is search-throughput evidence, not an empirical mean-guesses improvement.

`../benchmarks/predictive/release-gameplay-latency-scratch-v1.json`
reuses proposal scratch space and memoizes invariant `weight * log2(weight)` terms
within each search. Fast root completed 5 candidates rather than 3; allocated bytes
per call fell from 123.43 to 59.70 MiB. OLATE Fast retained 9 candidates and decreased
from 46.47 to 40.56 MiB. Work varies under wall deadlines: these are allocated-byte
totals, not live-memory savings or matched-node timing. Hard-mode allocated bytes
increased from 128.30 to 130.27 MiB, so the change is not a universal resource win.
After this run the weighted-log vector was made lazy to avoid allocating it in
terminal-only searches; that last allocation adjustment is not included in the run.

## Study resource measurements

September study/evidence latency uses the public artifact-free predictive request
at an explicit evaluation date, including request preparation and response work.
Rolling/study diagnostics use the declared development end; range evaluations use
their requested end. Sealed confirmation reuses the frozen development diagnostic
date. Evaluation hard-case selection is date-bounded too. These paths no longer
read the wall-clock day's posterior, which could introduce later history into an
earlier candidate's resource/selection evidence. Older latency figures retain
their historical measurement scope and must not be compared as identical protocols.

Study format v17 records process-lifetime peak working set only as a shared-process budget diagnostic. It is excluded from guarded candidate ordering and Pareto dominance: later candidates inherit earlier peaks, and restarting a process changes that history. Candidate-specific memory comparisons require isolated, matched processes before promotion. Serializing latency measurements removes worker contention but does not isolate memory. Earlier v16 memory-based rankings must not be treated as evidence of candidate memory savings.

## Interpretation

- The normal large-state proxy root is within the current interactive latency envelope on this machine.
- Bounded lookahead on the replayable tractable posterior remains under 100 ms warm on this machine, but its continuation work now costs more wall time than the highly parallel full-posterior proxy root.
- Pooled exact search is the most expensive measured regime, but remains below 200 ms on the replayable 15-answer state.
- Allocation volume grows from about 7.2 MiB at the proxy root to 38.2 MiB in pooled exact. Reusing scratch vectors and candidate buffers is the clearest low-level opportunity, but solve-quality studies take priority because the current working-set envelope is modest and premature rewrites would add risk.

## Reproduction

From the repository root in PowerShell:

```powershell
$env:MAYBE_WORDLE_PROFILE_OUTPUT = 'benchmarks/predictive/release-gameplay-latency-v1.json'
cargo bench --bench performance_profile
Remove-Item Env:MAYBE_WORDLE_PROFILE_OUTPUT
```

The artifact records the exact benchmark executable fingerprint, input/config fingerprints, git revision/dirty state, platform, CPU identifier, observations, and detected search regime.
Declared source inputs are checked before and after solver construction and again
after measurement. The generated pattern cache is bound after construction and
rechecked before publication. A changed input aborts publication; the run must be
restarted rather than attributed to the final on-disk input snapshot.

By default, the profiler measures all three existing phases: 30 ms preview, 250
ms Fast, and 2,000 ms Strong. Set the optional
`MAYBE_WORDLE_PROFILE_PHASE` to `preview`, `fast`, `strong`, or `baseline` to
measure only that phase. `baseline` uses the Fast budget and reply shortlist
with `baseline_only = true`; its budget identity is recorded in the selected
phase. A selected-phase artifact omits the unmeasured phase fields and records
the selection at the report level.

For candidate-specific process-lifetime peak working-set diagnostics, run each
candidate/phase as a separate benchmark process and give each result a distinct
output path. This keeps the fixed date, inputs, eight workloads, and sample
count identical while isolating the process high-water mark for that candidate:

Set `MAYBE_WORDLE_PROFILE_CONFIG` to an experimental TOML path to profile that
candidate without replacing `config/prior.toml`. Relative paths are resolved from
the repository root. The selected file is fingerprinted before and after the run;
an unreadable or invalid config is an error, not a fallback to production defaults.
Leave it unset for the production config. Preserve and restore any existing value
when changing this environment variable for a run.

```powershell
$oldPhase = $env:MAYBE_WORDLE_PROFILE_PHASE
$oldOutput = $env:MAYBE_WORDLE_PROFILE_OUTPUT
try {
    foreach ($phase in @('fast', 'strong', 'baseline')) {
        $env:MAYBE_WORDLE_PROFILE_PHASE = $phase
        $env:MAYBE_WORDLE_PROFILE_OUTPUT = "benchmarks/predictive/release-gameplay-latency-$phase-v1.json"
        cargo bench --bench performance_profile
        if ($LASTEXITCODE -ne 0) { throw "performance profile failed for $phase" }
    }
}
finally {
    if ($null -eq $oldPhase) {
        Remove-Item Env:MAYBE_WORDLE_PROFILE_PHASE -ErrorAction SilentlyContinue
    }
    else {
        $env:MAYBE_WORDLE_PROFILE_PHASE = $oldPhase
    }
    if ($null -eq $oldOutput) {
        Remove-Item Env:MAYBE_WORDLE_PROFILE_OUTPUT -ErrorAction SilentlyContinue
    }
    else {
        $env:MAYBE_WORDLE_PROFILE_OUTPUT = $oldOutput
    }
}
```

The selected phase is validated before configuration, model, or workload data
is loaded. In a debug build, the existing no-explicit-output early skip still
applies; provide an explicit output only when intentionally running the
profiler in debug mode.

`cargo test --all-targets` invokes benchmark binaries in a debug profile, so this benchmark exits early in that context unless `MAYBE_WORDLE_PROFILE_OUTPUT` is explicitly set. This prevents unoptimized test timings from overwriting the release artifact.

## Limitations

The bounded `../benchmarks/predictive/september-finite-regret-legality-hard-v1.json`
reuses compiled constraints across each recursive dictionary scan and formats
violations only for public diagnostics. The same six-state audit fell from 15.3 s
after non-progress pruning to 5.4 s. Fast selected reference-optimal `smite` on the
22-survivor state in the audit and five separate manual replays; Strong completed
the search. All six audited choices match the shared-kernel exhaustive reference
within floating-point precision. This is a fixed-workload observation, not a
general speedup estimate or a real-time guarantee under arbitrary system load.
The separate seven-day normal-mode screen remained at 3.5714, with zero failures;
no improvement in the overall gameplay mean has been established.

The September state-local baseline follow-up is recorded in
`../benchmarks/predictive/release-gameplay-latency-state-local-v1.json`.
The eight workloads took 28.9 seconds, excluding compilation. Fast median full-request
latencies were 263.89 ms at the root, 256.04 ms for OLATE/10001, 79.24 ms for the
13-answer broad state, 256.62 ms for fallback support, and 8.55 ms on the final turn.
Root Fast completed 8/9/9 candidate values across three samples; OLATE and fallback
completed ten each. Those broad-state values remain feasible-policy upper bounds,
not exact root optima. The 30 ms root preview remained heuristic. This run verifies
bounded response behavior after removing inherited root probes from the baseline;
it does not measure chronological solve quality or justify promotion. Three samples
per phase still cannot establish a population p95, and memory peaks remain shared
process diagnostics. Later baseline-only evaluation support requires fresh evidence.

The September 23 post-bound-pruning `../benchmarks/predictive/release-gameplay-latency-bound-pruning-v1.json`
uses the same fixed August 1 reachable states, eight workloads and three samples
per preview/Fast/Strong phase. Measurement took 33.7 seconds excluding release
compilation. Median full-request times (preview / Fast / Strong) were 38.77 /
264.03 / 2016.15 ms at root, 35.32 / 256.16 / 2006.06 ms at OLATE/10001,
35.87 / 266.64 / 1604.04 ms in hard mode, and 8.42 / 8.49 / 8.41 ms at the
late-turn state. Root, OLATE and fallback-tail retained completed feasible
upper-bound actions at Fast and Strong; tractable bands and hard mode returned
model-exact action values. The process peak working set was 169.9 MiB across
the run, not a candidate-specific memory value. Strong allocated about 400.4
MiB per root call and 459.4 MiB per OLATE call, most of it transient; neither
figure is live memory. Three-sample p95 remains the sample maximum. This
dirty-worktree diagnostic validates bounded responsiveness on those fixed
states only. Different executable identities and deadline-dependent work make
historical profile comparisons unsuitable as a causal speedup or gameplay-score
claim; full internal stage attribution still needs an opt-in profiler before further kernel
changes.
